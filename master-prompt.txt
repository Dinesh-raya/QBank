## 2. Actual reference document

The supplied reference file is `Model Test 13.pdf`.

Inspect this document before finalizing extraction and segmentation rules. Use its actual layout as the first benchmark for the application.

### Observed characteristics

The document is an eight-page IBPS RRB Clerk Prelims model test.

- Pages 1–4 contain Reasoning questions 1–40.
- Pages 5–8 contain Numerical Ability questions 41–80.
- Each question generally has five numbered answer options.
- Shared direction paragraphs introduce groups of questions.
- Several question groups continue across page boundaries.
- The document includes repeated page headers, page numbers, branding, a large diagonal watermark, and other decorative elements.
- Some content is embedded in a visual structure, including a line graph, a data table, mixed character sequences, and mathematical expressions.
- An answer key appears at the end, presented as compact question-number/answer-option pairs.
- The PDF has extractable text, but certain mathematical and visually arranged content requires validation against the rendered pages.

Treat these observations as the initial profile, not hard-coded rules for every future paper.

Do not assume all future papers are eight pages long, contain 80 questions, have five options, or use the same section names. Document length, question count, option count, section headings, answer-key format, and topic structure must be determined per document.

Do not infer a publication year from an edition or test number unless the document explicitly supplies it.

Keep the supplied PDF as a test fixture only if the user deliberately places it in the project’s test-data location. Do not commit private or copyrighted user documents to version control.

## 3. Main purpose and user workflow

The intended user is preparing for Indian bank and competitive examinations, particularly IBPS, SBI, RRB, Specialist Officer, LIC, and related examinations.

The primary workflow is:

1. Upload a question paper or answer-key document.
2. Detect its page structure and determine appropriate text-extraction or OCR methods.
3. Identify sections, shared instructions, individual questions, answer options, passages, puzzles, tables, graphs, and equations.
4. Suggest subject, topic, and subtopic classifications.
5. Extract an answer key when one is present.
6. Review uncertain or malformed content against the original document.
7. Confirm and save the questions in a persistent local database.
8. Browse, search, filter, edit, export, and back up the resulting question bank.

The central goal is faithful digitization and accurate organization. Automatic question solving is not the first priority.

## 5. Document inspection and page analysis

Before extracting individual questions, inspect the document.

Determine, where possible:

- Number of pages.
- Page dimensions and rotation.
- Available selectable text.
- Pages likely to contain scanned content.
- Page layout and column structure.
- Repeated headers and footers.
- Section headings and direction paragraphs.
- Likely question-number ranges.
- Presence of tables, charts, formulas, diagrams, and answer keys.

Process mixed PDFs at the page level. One document may contain both text-based pages and scanned pages.

Do not assume that nonempty extracted text means a page has been extracted correctly.

Track useful quality indicators, including suspicious characters, missing text, text density, OCR confidence where available, and inconsistencies in question numbering.

### Headers, footers, watermarks, and logos

The reference PDF includes repeated branding and a diagonal watermark. Similar documents may contain logos, barcodes, QR codes, page numbers, and running headers.

Prevent decorative content and watermark artifacts from being included in question statements.

Use repeated-position text detection, page-region analysis, and cautious cleanup rules where appropriate.

Do not globally delete a phrase simply because it appears several times. It might be a legitimate instruction or part of multiple questions.

Retain raw page extraction separately from cleaned page text so a user can investigate any cleanup error.

## 7. Question segmentation: highest-priority requirement

Identify individual questions and separate them from section headings, general instructions, shared passages, puzzles, tables, graphs, and unrelated page content.

Do not rely exclusively on regular expressions or the assumption that every question starts at the beginning of a new line.

Use document structure, question numbering, layout coordinates, option patterns, direction headings, contextual relationships, and manual review.

### Question records

Each question should have:

- A stable question ID.
- Original question number, when identifiable.
- Question text.
- Answer options as structured records.
- Primary subject, topic, and subtopic.
- Optional secondary tags.
- Source document ID.
- Original page number.
- Original source coordinates or page-image reference when available.
- Parent shared-context ID when applicable.
- Raw extracted text and corrected text stored separately.
- Optional correct answer.
- Optional explanation.
- Extraction method and quality indicators.
- Classification method and review status.
- Creation and modification timestamps.

The source page and original question number must be preserved even after manual corrections.

### Recognize common structures

Support:

- Standalone multiple-choice questions.
- Questions with varying numbers of options.
- Non-MCQ questions.
- Questions that continue across pages.
- Shared instructions followed by multiple questions.
- Shared puzzle or arrangement descriptions.
- Reading passages followed by multiple questions.
- Tables and graphs referenced by several questions.
- Questions containing formulas, unusual symbols, or inline expressions.
- Answer options printed in a single line or across multiple lines.

Do not assume that all answer options use identical formatting or that a question group ends at a page break.

## 8. Shared passages, instructions, and puzzle groups

This is critical for reasoning questions.

In the reference paper, one statement or clue set supports multiple questions. The application must recognize the relationship rather than treating the full shared text as an ordinary part of the first question.

Represent shared material as a separate context record with links to the associated questions.

Supported context types should include:

- General instructions.
- Logical statements and conclusions.
- Seating arrangements.
- Floor puzzles.
- Scheduling and ordering puzzles.
- Height or ranking problems.
- Coding-language examples.
- Mixed letter-number-symbol sequences.
- Reading passages.
- Data Interpretation charts and tables.
- Other shared stimuli.

Each linked question must remain independently searchable and classifiable.

Opening a question should display both its own text and the shared context it depends on.

The user must be able to attach or detach a question from a context and correct group boundaries.

For example, a group of six questions linked to one data table must retain one source table and six linked question records. It must not silently duplicate, truncate, or lose the table when a question is edited.

## 9. Special handling for the reference paper

Implement the following as explicit regression tests and design considerations.

These requirements are based on the supplied example; they must not become assumptions about all future PDFs.

### A. Section boundaries

The reference has a Reasoning section containing questions 1–40 and a Numerical Ability section containing questions 41–80.

Detect section headings and associate questions with their actual section. Allow section names and numbering to vary in other papers.

Check for missing numbers, duplicate question numbers, unexpected resets, and questions that cross page boundaries.

Do not automatically fabricate missing questions to complete an expected sequence.

### B. Shared reasoning question sets

The supplied paper has several multi-question groups.

The implementation must be able to preserve, among others:

- Questions 1–4: shared syllogism instructions.
- Questions 5–9: exam-date and month scheduling clues.
- Questions 10–14: a floor-arrangement puzzle.
- Questions 15–18: comparison or inequality statements.
- Questions 20–22: relative-height clues.
- Questions 24–28: a mixed sequence of letters, numbers, and symbols.
- Questions 30–34: an ordering puzzle about purchase occasions.
- Questions 35–39: coded-language examples.
- Questions 52–57: a shared line graph.
- Questions 61–66: a shared data table.

Do not infer that every question in a group has the same subtopic solely because it shares a stimulus. The topic must reflect what the individual question is testing.

### C. Preserve character sequences exactly

Questions based on letter, number, and symbol sequences must preserve:

- Character identity.
- Original left-to-right order.
- Repeated characters.
- Punctuation and operator symbols.
- Spaces where their interpretation matters.
- The actual operation described in the question.

Do not normalize a sequence by sorting, removing repeated characters, changing case, or dropping unfamiliar symbols.

Store the original sequence and support comparison with the source page.

If the character sequence cannot be extracted reliably, flag it for review rather than silently correcting it.

### D. Line graphs and Data Interpretation

Questions 52–57 share a line graph showing student participation across schools A–E.

Graph values may be presented visually, with labels and data points but no machine-readable underlying data table.

The application must preserve the source graph and page reference, even when its values cannot be extracted reliably.

Where possible, identify:

- Graph type.
- Axis labels.
- Axis scale.
- Category labels.
- Data points.
- Legend or series names.

Never invent graph values or assume they align with round numbers just because the graph looks approximate.

If graph values are manually transcribed, label them as user-verified. If values are machine-interpreted, label them as uncertain until verified.

A graph may be stored as an image or source-page crop with structured data attached separately. The visual source must remain accessible.

Every question that references the graph should link to the same graph context.

### E. Tabular Data Interpretation

Questions 61–66 use a shared table with shop names, months, and numerical values.

Preserve the original table layout or a clear table representation.

Where possible, store its structured rows, columns, labels, values, and source coordinates separately from the displayed image.

Do not confuse a row heading with a column header, or allow OCR column-order errors to alter data.

The user must be able to compare extracted values with the original table.

### F. Mathematical expressions and notation

Questions 68–80 contain expressions involving operations, powers, roots, fractions, decimals, and missing values.

Treat formulas as structured content, not merely plain-language text.

Preserve:

- Mathematical operators.
- Superscripts and exponents.
- Square-root and other radical symbols.
- Fraction numerators and denominators.
- Parentheses and grouping.
- Decimal values.
- Missing-value symbols such as question marks.
- Equality and inequality relationships.

Where practical, represent formulas using a structured mathematical or display format, while retaining the raw text and original page image.

LaTeX or MathML may be used for display if validated. Do not assume every formula can be converted perfectly to LaTeX.

If a symbol or fraction layout is uncertain, display the original formula image beside the extracted representation for correction.

Never silently interpret a malformed formula and claim that the original question contained that interpretation.

### Classification logic

Use a layered approach:

1. Transparent rules for obvious patterns.
2. Optional local AI suggestions for ambiguous questions.
3. Manual correction and confirmation.

Pass the question text, relevant shared context, and allowed taxonomy to the classifier.

Validate model responses against a strict schema and existing taxonomy.

The classifier must return structured data rather than an arbitrary paragraph. It must never invent new topics by default.

Store the classification method and review state.

Support primary classifications, secondary tags, and uncertain classifications requiring review.

Do not classify every question solely by its shared context. For example, questions based on a chart may test ratios, percentages, averages, or Data Interpretation. Use the individual question's task to determine its primary topic and use additional tags where appropriate.

Provide keyword-based fallback suggestions when local AI is unavailable.

Never fabricate a confidence percentage. Any confidence estimate should be clearly described as a heuristic unless validated empirically.

## 11. Answer-key extraction

The reference paper includes a compact answer key on its final page.

Implement a separate answer-key extraction stage.

Recognize common patterns such as:

- Question number followed by an option number.
- Question number followed by an answer letter.
- Numbered answer lists.
- Tabular answer-key layouts.
- Separate answer-key PDFs when uploaded.

For this particular reference paper, test whether the compact pairs can be parsed as question number and correct option number.

Do not assume that every future key uses this format.

For every extracted key entry, record:

- Question number.
- Extracted answer value or option index.
- Source document and page.
- Extraction method.
- Match status.
- Review status.

Validate answer-key entries against the actual set of extracted questions and options.

Detect missing entries, duplicate entries, out-of-range question numbers, invalid option indices, and ambiguous matches.

A missing answer must remain missing. Never infer the correct answer just because one is expected.

Display the answer key during review so the user can correct incorrect mappings.

Do not generate explanations or solve the questions automatically in the first release.

## 12. Database design

Use SQLite with a normalized schema and a dedicated database-access layer.

Implement tables or equivalent relations for:

- Documents.
- Pages.
- Sections.
- Shared contexts or stimulus groups.
- Questions.
- Answer options.
- Taxonomy entries.
- Question classifications and secondary tags.
- Answer-key entries.
- Review history.
- Processing jobs or page-level processing status, where needed.

Use stable IDs and foreign-key relationships.

Important requirements:

- A question can belong to one source document and page.
- A question can link to a shared context.
- A context can be linked to multiple questions.
- Options retain their intended order.
- The correct answer can be absent.
- A question can have multiple tags.
- Raw extraction and corrected content are stored separately.
- Processing and review status are explicit.
- Answer-key provenance is retained.
- Source pages and original documents can be retrieved.

Use parameterized SQL, transactions, indexes, schema migrations, and error handling.

Do not store the entire question bank as one large JSON value.

Do not delete an original question just because it may be a duplicate.

## 13. Duplicate detection

Detect potential duplicates using:

- Source-document hashes.
- Normalized question text.
- Optional similarity matching when justified.

Do not merge or delete questions automatically.

Two questions with similar wording may use different numbers, options, passages, or charts.

Allow the user to review likely duplicates and mark them as identical, related, or distinct.

Repeated questions from separate papers should retain their separate source references even when their content is identical.
